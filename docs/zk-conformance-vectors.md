# Cross-Layer Verifier Conformance Vectors

Harpocrates parses the same verifier material in four places: the Noir circuit
defines it, the Python backend forwards it, the browser produces it, and the
Soroban registry acts on it. If any two of those disagree about what a valid
public-input frame is, the disagreement is a soundness bug — one layer accepts
what another rejects, and an attacker picks the gap.

This document defines the canonical codec, the shared corpus that pins it, and
how each layer is held to it.

## The codec: `hpx-vi/1` and `hpx-vi/2`

One canonical implementation per layer, all agreeing byte for byte:

| Layer | Implementation | Runner |
| --- | --- | --- |
| Backend | `backend/verifier_inputs.py` | `backend/test_conformance_vectors.py` |
| Browser | `frontend/src/verifierInputs.ts` | `frontend/src/verifierInputs.conformance.test.ts` |
| Contract | `contracts/contracts/harpocrates-registry/src/verifier_inputs.rs` | `contracts/contracts/harpocrates-registry/src/test_conformance.rs` |

Two corpora pin the codec, regenerated by `python zk/vectors/generate_vectors.py`:

- `zk/vectors/verifier_conformance_v1.json` — the original `hpx-vi/1` frames.
- `zk/vectors/verifier_conformance_v2.json` — `hpx-vi/2`, which appends a
  circuit version trailer so the wire format commits to the exact circuit that
  produced the proof.

### Frame layout

A silent-witness public-input frame is exactly **160 bytes**: five 32-byte
big-endian BN254 field elements. Revocation-witness frames remain 128 bytes.

`silent_witness/v1`

```
[  0.. 32)  video_hash_hi     16 zero bytes of padding, then the high 16 bytes
[ 32.. 64)  video_hash_lo     16 zero bytes of padding, then the low 16 bytes
[ 64.. 96)  credential_root
[ 96..128)  nullifier
[128..160)  domain_tag          SHA-256(protocol || version || network)
```

`revocation_witness/v1`

```
[  0.. 32)  revocation_root
[ 32.. 64)  nullifier
[ 64.. 96)  domain_separator   must equal REVOCATION_DOMAIN_SEPARATOR
[ 96..128)  credential_root
```

`silent_witness/v2` is the 160-byte `silent_witness/v1` layout plus a trailing
circuit version:

```
[  0..160)                  exactly the silent_witness/v1 frame
[160..192)  circuit_version  uint32 big-endian in the low 4 bytes; upper 28 zero
```

`silent_witness/v2` has no `verifier_scope` / `epoch` half-fields; it is the
*classify-side* framing of the same public inputs that the circuit commits.
(The on-chain *registration* envelope is the 224-byte scoped frame plus a
32-byte trailer, i.e. 256 bytes total; the trailer `[224..256)` carries the
same uint32 circuit version.)

The domain separator is seven bytes of BN254 padding followed by the 25 ASCII
bytes of `HARPOCRATES_REVOCATION_V1`, i.e.
`00000000000000484152504f4352415445535f5245564f434154494f4e5f5631`. It is
byte-identical to `REVOCATION_DOMAIN_SEPARATOR` in the registry contract, and
the Rust runner asserts that directly rather than through a case.

### Canonical check order

The order is part of the contract — two layers that reject the same input for
different reasons are still a divergence, because operators and clients branch
on the code:

1. `length` — frame is not exactly the schema-specific length (160 bytes for
   `silent_witness/v1`, 128 bytes for `revocation_witness/v1`)
2. `padding` — a 128-bit half has a non-zero high 16 bytes (`silent_witness` only)
3. `non_canonical_field` — a field element is ≥ the BN254 scalar modulus, checked in index order
4. `zero_field` — a required identity field is zero, checked in index order
5. `domain_mismatch` — domain separator mismatch (`revocation_witness` only)
6. `proof_undersize` — proof blob below `MIN_PROOF_BYTES` (64)
7. `proof_oversize` — proof blob above `MAX_PROOF_BYTES` (65 536)

Public inputs are always classified before the proof blob.

The `hpx-vi/2` order inserts the circuit-version check immediately after
padding and restricts the later checks accordingly:

1. `length` — frame is not exactly 192 bytes for `silent_witness/v2`
2. `padding` — a 128-bit half has a non-zero high 16 bytes (both `silent_witness` schemas)
3. `version_mismatch` — the trailing circuit version's upper 28 bytes are
   non-zero, or the u32 value differs from `expected_circuit_version` (2)
4. `non_canonical_field` — checked only on fields `[0..4]` (the two video-hash
   halves, credential root, nullifier); the domain tag is compared byte for
   byte, never canonicalized
5. `zero_field` — checked only on `credential_root`, `nullifier`, `domain_tag`;
   a zero `video_hash` is structurally legal
6. `domain_mismatch` — domain tag differs from `silent_witness_domain_tag_hex`
7. `proof_undersize` / `proof_oversize` — proof blob outside 64..=65536

The check order is a contract, not an implementation detail: two layers that
reject the same input for different reasons are still a divergence, because
operators and clients branch on the code.

`unknown_schema` remains layer-local (schema dispatch is not a wire input) and
is exercised outside both corpora.

`malformed_hex` is also layer-local — hex decoding only happens where material
arrives as a string (backend and browser) — but it is pinned by a companion
corpus: `zk/vectors/malformed_public_inputs_v1.json`, regenerated by
`python zk/vectors/generate_malformed_public_inputs.py`. The Soroban registry
receives bytes and does not consume that file.

## Vector format

```json
{
  "format": "harpocrates.verifier-conformance",
  "version": 1,
  "codec": "hpx-vi/1",
  "constants": { "public_inputs_len": 160, "min_proof_bytes": 64, "...": "..." },
  "schemas": { "silent_witness/v1": ["video_hash_hi", "..."] },
  "reject_codes": ["length", "padding", "..."],
  "cases": [
    {
      "id": "sw-neg-020-credential-root-equals-modulus",
      "schema": "silent_witness/v1",
      "description": "A field element equal to the modulus is a non-canonical encoding.",
      "public_inputs_hex": "...",
      "proof_hex": "...",
      "expect": { "accept": false, "reject_code": "non_canonical_field" }
    }
  ]
}
```

The `hpx-vi/2` corpus carries `"version": 2`, `"codec": "hpx-vi/2"`, the extra
constants `silent_witness_v2_public_inputs_len` (192) and
`expected_circuit_version` (2), schema `silent_witness/v2` (fields incl.
`circuit_version`), and `version_mismatch` in `reject_codes`. Its case ids use
the `sw2-pos-` / `sw2-neg-` prefixes.

Case ids are stable and structured: `<schema>-<pos|neg>-<nnn>-<slug>`. The
structural corpus covers positive frames plus negative framing, padding, field
canonicity, zero identity fields, domain binding, cross-schema length traps,
circuit-version mismatch, and proof size bounds.

### Malformed public-input hex corpus

```json
{
  "format": "harpocrates.malformed-public-inputs",
  "version": 1,
  "codec": "hpx-vi/1",
  "reject_codes": ["malformed_hex"],
  "cases": [
    {
      "id": "mh-neg-030-0x-prefix",
      "field": "public_inputs",
      "description": "A 0x prefix is a presentation form, not part of the wire alphabet.",
      "value": "0x00",
      "expect": { "reject_code": "malformed_hex" }
    }
  ]
}
```

Case ids are `mh-neg-<nnn>-<slug>`. The corpus covers odd-length strings,
non-hex alphabet, whitespace/control characters, `0x`/`#` decorations, empty-ish
tokens, and non-ASCII lookalikes. Backend and browser runners assert every case
rejects with `malformed_hex` and that the rejection signal never echoes the
input presentation.

## Artifact binding

Each runner asserts more than the cases:

- Constants in the corpus (`public_inputs_len`, `min_proof_bytes`,
  `max_proof_bytes`, the modulus, the domain separator) must equal the
  implementation constants. A corpus that drifts from the code fails before any
  case runs.
- `codec` and `version` must match what the runner expects.
- CI regenerates the structural corpus from `generate_vectors.py` and the
  malformed-hex corpus from `generate_malformed_public_inputs.py`, then `diff`s
  each against the committed file, so a hand-edited corpus — which would
  silently weaken every layer's assertions — fails.

## The real boundary

The contract runner drives **both** contract-side boundaries:

1. the pure `verifier_inputs` codec, and
2. the real on-chain entry point `classify_public_inputs(schema_id,
   public_inputs, proof_len)`, invoked through the generated contract client.

`classify_public_inputs` is read-only, side-effect free, and O(1) in the frame
size. It returns `0` for accepted material or the stable numeric reject code. It
takes a proof *length* rather than a proof blob, so classification never
transports proof material on chain.

`test_conformance.rs` also asserts the entry point is idempotent and consumes no
nullifier, and that an unknown `schema_id` returns a code rather than panicking.

## Compatibility and migration

`classify_public_inputs` gained `silent_witness/v2` **additively**; the
`hpx-vi/1` handling is byte-for-byte unchanged, and an unknown schema id still
returns a code rather than panicking.

On the registration paths (`register_anonymous_verified` and friends), #368
made the versioned envelope opt-in rather than a forced break:

- A bare 224-byte scoped frame is the legacy `scoped_nullifier/v1` layout and is
  treated as an implicit circuit version 1 — exactly the pre-#368 behavior, so
  *legacy v1 proofs keep registering*.
- A 256-byte envelope appends a 32-byte `circuit_version` trailer that must
  decode to `EXPECTED_CIRCUIT_VERSION` (2); anything else is rejected with
  `CircuitVersionMismatch`.

Provers must switch to emitting the versioned envelope for new proofs so the
wire format commits to the exact circuit; old proofs remain verifiable. The
migration steps therefore were:

1. Confirm every in-flight prover emits canonical frames (use
   `classify_public_inputs` as a pre-flight — that is what it is for).
2. Ship the v2 codec id (`hpx-vi/2`) and the envelope trailer behind the new
   constants, without tightening any existing function's accepted lengths in
   place (a 224-byte frame must still register as v1).
3. Update both corpora `version` fields and this document in the same commit.

**Rollback:** deploying a pre-#368 wasm removes `classify_public_inputs`,
rejects the 256-byte envelope (224-byte-only, as before), and restores the
previous surface exactly. Nothing persists that a rolled-back contract would
misread — the entry points write no storage.

## Running the runners

```bash
# Python
cd backend && python -m pytest test_conformance_vectors.py -q

# Browser
cd frontend && npx vitest run src/verifierInputs.conformance.test.ts

# Contract
cd contracts && cargo test --workspace conformance
```

CI runs all three: the Python runner in `zk-ci.yml`, the Rust runner in
`contracts-ci.yml`, the TypeScript runner in `frontend-ci.yml`. Both contract
and frontend workflows trigger on `zk/vectors/**`, so a corpus change re-runs
every layer.

## Mismatch diagnostics

A divergence fails exactly one of the three suites and names the offending case
id, so diagnosis does not require re-deriving which layer is wrong:

```
sw-neg-020-credential-root-equals-modulus: expected 'non_canonical_field', got None
```

The Rust runner collects **all** mismatches before asserting, so a systematic
divergence shows as a list rather than one case at a time.

## Privacy

Rejections carry a stable machine code and at most a field *name* — never
witness material, proof bytes, or public-input bytes. `VerifierInputError.signal()`
(Python) and `VerifierInputError.signal()` (TypeScript) return exactly
`{codec, reject_code, field?}`, and both runners assert that a rejection of a
tampered frame does not echo any part of that frame. The contract collapses all
codec rejections onto the pre-existing `InvalidPublicInputs` / `InvalidProof`
errors, so the on-chain error surface discloses nothing new.

## Limitations

- The corpus pins *structural* agreement. It does not pin cryptographic
  agreement: whether all four layers accept the same **proofs** requires real
  proving artifacts, which is the reproducible-build pipeline's job
  (`docs/zk-reproducible-builds.md`).
- The v2 corpus pins the version *signal* (a frame must carry
  `circuit_version == 2`), not the domain-tag constant itself — which the v1
  corpus and the contract's `expected_domain_tag` already pin. Regenerating the
  circuit with a new version forces `EXPECTED_CIRCUIT_VERSION`,
  `CURRENT_CIRCUIT_VERSION`, and this corpus to move in lockstep.
- The Noir circuit itself is not a runner. It defines the layout the corpus
  encodes, but `nargo test` does not consume the JSON. Circuit-side drift is
  caught indirectly, when regenerated artifacts change the frame the other three
  layers see.
- The Rust runner reads the corpus with a small line-oriented scanner rather
  than a JSON crate, to keep third-party code out of a contract crate. It
  depends on the generator's stable key ordering; a structurally reordered
  corpus parses as zero cases, which `corpus_is_non_empty_and_versioned`
  rejects.
