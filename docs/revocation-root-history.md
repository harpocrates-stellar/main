# Bounded Revocation Root History & Grace Window

Implemented in `contracts/contracts/harpocrates-registry/src/lib.rs`, tested in `src/test_revocation.rs` and `src/test_budget.rs`.

## Motivation & Context

Previously, `set_revocation_root` overwrote `DataKey::RevocationRoot` in place and `check_non_revocation` accepted only the single current root. Any non-revocation proof generated by a user against root $R_{t-1}$ immediately before an admin published $R_t$ failed on arrival with `InvalidPublicInputs` (`#10`), racing against client proving latency and network submission time.

To eliminate this proving-time race while keeping on-chain state strictly bounded, the registry stores the last $N = 4$ revocation roots (`MAX_REVOCATION_ROOT_HISTORY`) together with their activation ledger sequence in a persistent ring buffer (`DataKey::RevocationRoots`) and accepts recent previous roots within a configurable ledger grace window (`DataKey::RevocationRootGraceWindow`).

## Storage & Ring Buffer Design

| Constant | Value | Meaning |
| --- | --- | --- |
| `MAX_REVOCATION_ROOT_HISTORY` | `4` | Maximum number of `RevocationRootEntry` items retained in `DataKey::RevocationRoots`. |
| `DEFAULT_REVOCATION_ROOT_GRACE_LEDGERS` | `120` | Default grace window in ledgers (~10 minutes at ~5s/ledger) when not explicitly set. |
| `MAX_REVOCATION_ROOT_GRACE_LEDGERS` | `17_280` | Maximum configurable grace window in ledgers (~24 hours at ~5s/ledger). |

Each entry in `DataKey::RevocationRoots` is a `RevocationRootEntry`:

```rust
pub struct RevocationRootEntry {
    pub root: BytesN<32>,
    pub activation_ledger: u32,
}
```

When `set_revocation_root(admin, revocation_root)` is called:

1. `DataKey::RevocationRoot` continues to be updated to `revocation_root` so current-root queries (`get_revocation_root()`) and existing callers behave identically.
2. Any duplicate occurrence of `revocation_root` in `DataKey::RevocationRoots` is removed so re-publishing a root refreshes its position at the tail.
3. If the vector length is at `MAX_REVOCATION_ROOT_HISTORY` (4), the oldest entry at the front is evicted before appending `{ root: revocation_root, activation_ledger: env.ledger().sequence() }`.
4. Storage growth is strictly $O(1)$ and bounded at 4 entries regardless of how many root rotations occur over the lifetime of the contract.

## Contract API

```rust
// Admin-only: publish a new revocation root and record its activation ledger in the ring buffer.
set_revocation_root(admin: Address, revocation_root: BytesN<32>)

// Public read: return the latest (current) revocation root, if any.
get_revocation_root() -> Option<BytesN<32>>

// Public read: return the bounded ring buffer of recent revocation roots (oldest to newest, up to 4).
get_revocation_roots() -> Vec<RevocationRootEntry>

// Admin-only: configure the grace window in ledgers (0..=MAX_REVOCATION_ROOT_GRACE_LEDGERS).
set_revocation_root_grace_window(admin: Address, grace_ledgers: u32)

// Public read: return the active grace window in ledgers.
get_revocation_root_grace_window() -> u32
```

## Verification & Grace Window Semantics

When `check_non_revocation(public_inputs, proof)` is invoked:

1. **Current root (unchanged):** If `parsed.revocation_root == DataKey::RevocationRoot`, the root check passes immediately regardless of how many ledgers have elapsed since the current root was published.
2. **Historical root within grace window:** If `parsed.revocation_root` does not match the current root, the contract searches `DataKey::RevocationRoots`. A historical entry is accepted if and only if:
   - `grace_ledgers > 0`,
   - `current_ledger - entry.activation_ledger <= grace_ledgers`, and
   - `current_ledger - reference_ledger <= grace_ledgers` (where `reference_ledger` is the activation ledger of the superseding entry).
3. **Rejection:** If the root is not in the 4-entry ring buffer (never existed or was evicted by subsequent rotations) or the ledger has advanced past the grace window, `check_non_revocation` reverts with `RegistryError::InvalidPublicInputs` (`#10`).

## Threat Model Implications

1. **Bounded revocation-lag window vs. proving liveness:** Accepting a recent previous revocation root within `grace_ledgers` introduces a bounded staleness window for revocation tree updates: a credential added to the revocation tree in $R_t$ could still produce a valid non-revocation proof against $R_{t-1}$ until `grace_ledgers` elapse (or until $R_{t-1}$ is evicted).
2. **Defense-in-depth via on-chain credential root check:** `check_non_revocation` always calls `require_active_credential_root(&env, &parsed.credential_root)` against live contract storage (`DataKey::CredentialRootV2`). If a credential's root is directly revoked on-chain via `revoke_credential_root`, `check_non_revocation` immediately rejects the proof with `RevokedCredentialRoot` (`#12`), even if the proof references a previous `revocation_root` still inside the grace window.
3. **Emergency revocation cut-off:** In an incident where an admin must immediately invalidate all previous revocation roots without waiting for `grace_ledgers` to expire, the admin can either:
   - Call `set_revocation_root_grace_window(admin, 0)` to disable the grace window immediately so only the current root is accepted, or
   - Call ` revoke_credential_root` directly for the compromised credential root.
4. **Nullifier replay protection across roots:** Nullifiers are stored in `DataKey::VerifierNullifier(verifier, nullifier)` independent of which revocation root in the ring buffer was matched. A proof cannot be replayed against another root in the history buffer using the same nullifier (`DuplicateNullifier`, `#6`).
5. **Storage and CPU exhaustion resistance:** Because the ring buffer is capped at `MAX_REVOCATION_ROOT_HISTORY = 4` and the grace window is capped at `MAX_REVOCATION_ROOT_GRACE_LEDGERS = 17_280`, neither a buggy client nor repeated admin rotations can cause unbounded storage growth or linear scan degradation.
